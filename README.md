## 参数说明

- `-c:v libsvtav1`: 使用 AV1 编码器，压缩效率高于 H.264 / H.265。
- `-crf 28`: 质量优先模式，本次选的是偏保守值，优先保证观感。
- `-preset 6`: 编码速度和压缩率的折中点，适合后续批处理。
- `-pix_fmt yuv420p`: 保持常见播放器兼容性。
- `-svtav1-params tune=0:film-grain=0`: 通用视觉优化，不额外注入胶片颗粒。
- `-c:a copy`: 音频不重编码，避免音频质量损失。
- `-movflags +faststart`: 将 `moov` 移到文件头，方便在线播放和快速起播。
- `-map '0:a:0?'`: 有音频就带上，没有也不报错，适合批量任务。

## 第二版参数说明

- `-c:v libx265`: 使用 H.265 / HEVC，压缩率高，同时比 AV1 更容易本地直播。
- `-preset medium`: 比 `slow` 快一档，适合批量处理时优先保证吞吐。
- `-crf 31`: 比第一版更激进，进一步压缩视频体积。
- `-tag:v hvc1`: 提升 Apple 生态内播放器识别和硬解兼容性。
- `-c:a aac_at -b:a 48k`: 音频压到 `48 kbps`，兼顾体积和兼容性。
- `-ac 1 -ar 24000`: 保持单声道和原采样率，避免无意义放大音频数据量。

## 第三版参数说明

- `-b:v 24k -maxrate 28k -bufsize 56k`: 直接按目标体积思路压视频码率，而不是单纯用 CRF。
- `-b:a 24k`: 把音频进一步压到 `24 kbps`。
- `-x265-params 'aq-mode=1:keyint=250:min-keyint=1'`: 去掉最重的细节分析参数，优先提高批量速度。
- 这套参数已经属于明显有损的激进档，适合“先保可播放，再极限缩体积”的场景。

## 第三版为什么会过压

- 我把编码策略从 `CRF` 改成了极低码率 `ABR`。
- 我把音频从 `48k` 继续砍到了 `24k`。
- 目标视频码率写成了 `24k`，但这个素材本身是 `1 fps`、内容复杂度低，`x265` 在这种素材上会明显低于名义目标码率输出。
- 最终视频实际只剩约 `7.4 kbps`，这就是“比目标更小、而且明显发糊”的直接原因。

## 第四版参数说明

- 改成 `2-pass` 两遍编码，目的是把体积打准，同时默认使用 `medium` 提高速度。
- 视频码率回到 `31k`，比第三版的实际 `7.4k` 高很多，画面会明显好于第三版。
- 音频压到 `16k`，把体积预算更多让给视频。
- 这版是“贴目标体积”的精确档，不是“极限最小体积档”。

## 为什么这版还能继续压缩

这次成品里，视频已经从约 `131 kbps` 降到了约 `42 kbps`，但音频仍然保留在约 `96 kbps`。  
也就是说，当前文件继续缩小的主要空间已经不在视频，而在音频。

## 当前 WebUI

- 上传区只保留批量选择文件，不再显示源文件列表、拖拽排序或选择框。
- 左侧只显示两项状态: 已上传文件总数、当前正在处理的文件。
- 右侧只显示已经处理完成、可以直接下载的视频。
- 处理完成后会显示 `打包下载 ZIP`。
- 批量处理默认使用第四版固定参数，不在页面里暴露可编辑项。
- 页面按浏览器会话 cookie 隔离，每个客户端只看见自己的上传、任务和导出。
- 上传文件会落在 `uploads/<clientId>/`，导出文件会落在 `exports/<clientId>/`。
- 左侧 `删除` 会清空当前客户端自己的上传目录。
- 右侧 `删除` 会清除当前任务对应的源文件和已完成视频，只影响当前客户端。
- 已完成视频默认保留原文件名，只有在同名冲突时才会自动补后缀。
- 上传区支持拖拽文件到页面或拖拽到上传框内。
- 页面提供两个 HEVC 预设:
  - `H.265 / HEVC` 是更小的压缩档，音频压得更低。
  - `libx265 + hvc1 + AAC` 还是同一个 HEVC 视频编码，只是音频更宽松，所以体积会略大。
- 页面还提供 `H.264` 预设:
  - 兼容性最好，Win10 默认播放器更稳。
  - 当前版本先压低音频，再收紧视频码率，属于“体积优先但保兼容”的方案。
  - 一般还是会比 HEVC 更大，但已经比纯兼容档更克制。
- 这里真正影响体积的是音频码率，不是 `hvc1` 标签本身。
- 每个浏览器会话有自己的上传目录、任务队列和并行槽位，不会和别人的任务互相排队。
- `并行处理` 可以给当前会话单独选择 1、2 或 3 个视频同时处理。
- 已完成视频会显示 `打包下载 ZIP`，只有当前会话自己能下载自己的导出结果。

## 后续做批量压缩时的建议

如果目标是“尽量不影响画质”，优先固定以下参数：

```bash
-c:v libsvtav1 -crf 28 -preset 6 -pix_fmt yuv420p -svtav1-params tune=0:film-grain=0 -c:a copy -movflags +faststart
```

如果后续你接受“音频轻微有损，但总体观感基本不变”，可以继续试这一版：

```bash
-c:a libopus -b:a 48k
```

这样通常还能再明显缩小一截，尤其是以人声为主的内容。

## 批量化命令模板

```bash
for f in *.mp4; do
  ffmpeg -y -i "$f" \
    -map 0:v:0 \
    -map '0:a:0?' \
    -c:v libsvtav1 \
    -crf 28 \
    -preset 6 \
    -pix_fmt yuv420p \
    -svtav1-params tune=0:film-grain=0 \
    -c:a copy \
    -movflags +faststart \
    "${f%.*}_av1_q28.mp4"
done
```

## 本次结论

如果优先考虑“压得更狠，而且本机更容易播放”，当前更适合作为默认方案的是第二版：

- 文件体积从 `198M` 降到 `79M`
- 实测总压缩约 `60.14%`
- 视频约 `41.9 kbps`
- 音频约 `48.0 kbps`
- 使用 `MP4 + hvc1 + AAC`，兼容性明显好于第一版 `AV1 in MP4`
- 适合直接扩展成批量压缩脚本

如果优先考虑“极限压缩体积”，第三版是当前最激进的方案：

- 文件体积从 `198M` 降到 `28M`
- 实测总压缩约 `85.79%`
- 视频约 `7.4 kbps`
- 音频约 `24.0 kbps`
- 兼容性仍然保持在 `MP4 + hvc1 + AAC`
- 画质牺牲会明显大于第二版
